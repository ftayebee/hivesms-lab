# 11 · Laravel API: reference, migration matrix, deployment

Status (2026-10-07): the Laravel API in `backend/` implements the complete backend of the Next.js
app (every route handler, every server action, every page-level query) on the existing database.
The Next.js app is **unchanged** and still runs on Prisma; switching it to this API is the next
step (§ 12). Audit and decisions: [10-laravel-api-audit.md](10-laravel-api-audit.md).
Customer API spec (OpenAPI 3.1): [backend/docs/openapi-public.yaml](../backend/docs/openapi-public.yaml).

## 1. Architecture

```
Next.js (server components / server actions = BFF)            customers' servers        SMS / payment providers
        │  Authorization: Bearer <session token>                 │ Bearer sfk_live_…          │ signed webhooks / IPN
        ▼                                                          ▼                            ▼
 routes/api.php ── middleware (request id, auth, tenant + permission | platform role | API key scopes,
        │           DB rate limit, verified email, Idempotency-Key)
        ▼
 Controllers (Api/V1/<Domain>) ── Form Requests (validation) ── API Resources (serialization)
        ▼
 Services (app/Services/<Domain>) ── DB::transaction + row locks ── Eloquent (42 models, existing schema)
        ▼                                                                  ▼
 Jobs (database queue) + Scheduler (sms:work every minute)            MySQL / MariaDB 10.4+
```

### Authentication
- **One session system** — the existing `sessions` table. Login/register return an opaque token once
  (32 random bytes, base64url; only `sha256(token)` stored). The Next.js server keeps it in its
  httpOnly cookie and calls Laravel with `Authorization: Bearer <token>`. Sessions created by the
  Node app are accepted as-is (tested), so nobody is logged out at cutover. No Sanctum (it would add
  a second, incompatible token table).
- Passwords: argon2id with the Node parameters; existing hashes verify (tested).
- Lockout 5 failures → 15 min; DB rate limits per IP and per account; timing equalisation for
  unknown accounts; suspended users rejected; sessions older than a password change are invalid.
- Email verification (24 h) and password reset (1 h, one-time, revokes all sessions); phone OTP.
- Bearer tokens are not sent automatically by browsers → no CSRF surface; CORS has no credentials.

### Authorization
| Layer | Mechanism |
|---|---|
| Organization (tenant) | `tenant:<permission,…>` middleware builds the tenant context from the session's active organization and the member's role permissions (`role_permissions`, editable per org). Every service query is scoped by `organizationId`; other tenants' ids return **404** (no existence leak). |
| Platform staff | `platform:<permission>` middleware; matrix USER/SUPPORT/ADMIN/SUPER_ADMIN × 14 `admin:*` permissions (same as Node). Customers never pass. |
| Customer API | `api.key:<scope,…>` middleware: key hash lookup, revoked/expired/IP allowlist/organization status, scopes. |
| Gates | `org:<permission>` and `platform:<permission>` gates mirror the middleware for ad-hoc checks. |
| Defence in depth | Services re-check permissions (`TenantContext::requirePermission`) even when middleware already did. |

Policies: the Node app has no per-model rules beyond "same organization + permission", which the
scoped service queries enforce (404 for foreign ids, tested per resource). Separate Policy classes
would duplicate that logic, so none were added; gates cover the permission matrix.

### SMS
`app/Services/Sms`: `SmsProviderInterface`, `SmsProviderManager` (admin-configured provider, secrets
decrypted from `settings`), `Providers/MockSmsProvider` (deterministic simulator), `Providers/HttpSmsProvider`
(generic gateway; ⚠ unverified scaffolding exactly like the Node one), `MessageSegmentCalculator`
(GSM-7/UCS-2, byte-identical to the Node implementation — verified against fixtures generated by
the Node code), `SmsCostCalculator` (rates, VAT, top-up maths, bcmath — no floats).
`app/Services/Messaging`: `SendService` (validate → sender → price → [lock wallet → limits → debit →
insert] → audit), `DispatcherService` (lease-based claiming, retries 30 s…30 min, max 4 attempts),
`DeliveryService` (forward-only status machine, idempotent events, refunds, campaign counters,
customer webhooks), `InboundService`, `ComplianceService`, `RiskEvaluator`, `LowBalanceService`,
`OutboundWebhookService`, `WorkerService`.

### Wallet
Balance changes only via `WalletService::debit/credit` inside a transaction: conditional
`UPDATE … WHERE balance >= amount` (never negative; DB CHECK as last line), ledger row with
`balanceAfter`, unique `(reason, referenceType, referenceId)` → a charge, refund or top-up can never be
applied twice. Sends lock the wallet row first, so concurrent sends of one organization serialise
on it (daily/monthly limits are checked under the same lock). A 5-process race test proves it.
Money is `DECIMAL(14,4)` handled as strings with bcmath.

### Payments
Providers `mock` (non-production / staging flag), `manual` (reference → admin verification),
`sslcommerz` (⚠ unverified, as in Node; redirect + IPN, always re-validated with the gateway API;
failure callbacks never change state). `PaymentService::complete` is the only credit path:
row-locked payment, conditional status transition, ledger key `(TOPUP, payment, id)`, invoice
unique per payment with gap-free number (`counters`), amount check against the gateway-confirmed
amount. Duplicate IPNs/clicks → `already_completed`, no second credit (tested).

### Queues and scheduler
| What | How |
|---|---|
| SMS send queue | the `messages` table (status QUEUED + `nextAttemptAt`, lease `lockedUntil`) — retry state lives on the row, claims are atomic, safe with any number of workers and with the Node worker during the transition |
| `sms:work` (every minute, `withoutOverlapping`, `onOneServer`, 45 s budget) | launch due campaigns → send batches → cancel leftovers of cancelled campaigns → poll delivery → finalise campaigns → deliver customer webhooks |
| `LaunchCampaignJob` (unique per campaign, 3 tries) | charge once + queue messages, then send small campaigns immediately |
| `DispatchMessagesJob` (after response) | sends API messages right after the HTTP response; anything missed is sent by `sms:work` |
| `ProcessContactImportJob` | CSV imports larger than 512 KB; status via `GET /app/contacts/imports/{id}` |
| `TransactionalMail` (queued, 3 tries) | every email; mail problems never fail a request |
| `app:housekeeping` (every 10 min) | expire 48 h-old online payments, purge sessions / rate-limit buckets / idempotency keys / old tokens |
| `queue:work --stop-when-empty` (every minute) | drains the database queue on hosts without Supervisor (`QUEUE_WORKER_VIA_SCHEDULER=true`) |

### Webhooks
Inbound: `POST /webhooks/sms/{provider}` (delivery), `…/inbound` (STOP), `POST /webhooks/payments/{provider}`,
`GET|POST /payments/{provider}/return`. Signature verified (HMAC-SHA256, constant time) before
parsing; unsigned rejected in production; each event stored once (`inbound_webhook_events.eventKey`
unique) and applied through the forward-only status machine → replays never double-count or
double-refund (tested). Outbound: signed `t=…,v1=…`, SSRF re-check before each delivery, 8 attempts.

### Rate limits (fixed window, `rate_limit_buckets`, shared with the Node app; `config/smsflow.php`)
| Rule | Limit |
|---|---|
| login per IP / per account | 20 / 10 per 10 min |
| register per IP | 5 / h |
| password reset per IP | 5 / h |
| OTP / resend verification per user | 5 / h |
| public forms per IP | 5 / 10 min |
| API per key (`API_RATE_LIMIT_PER_MINUTE`) | 600 / min |
| API send per key (`API_SEND_RATE_LIMIT_PER_MINUTE`) | 120 / min |
| API auth failures per IP | 30 / 5 min |
| provider webhooks per IP | 1,200 / min |
| dashboard per user per route (`DASHBOARD_RATE_LIMIT_PER_MINUTE`) | 300 / min |
| dashboard send/submit per user | 30 / min |
| admin per user per route | 120 / min |

## 3. Response conventions

- Envelope unchanged: `{success, data, meta:{requestId}}` / `{success:false, error:{code, message, details?}, meta}`.
- Validation: `422 VALIDATION_ERROR`, `details.fields: [{path, message}]` (existing contract).
- Business errors with a field: `details.field` (e.g. `{"field": "phone"}`) — what the forms use today.
- Lists: `data: [...]`, `meta: {page, pageSize, total, totalPages, …}`; page sizes as in the app
  (contacts 25, campaigns 20, transactions 30, reports 25, admin 25).
- Dashboard/admin JSON: camelCase (column names), enums as strings, money as decimal strings,
  dates ISO-8601 UTC with ms. Customer API and the 6 pre-existing admin endpoints keep snake_case.
- Downloads (CSV, documents) stream with `Cache-Control: private, no-store`; CSV cells are
  injection-safe.

`app/campaigns/{id}/export` → `/app/campaigns/{id}/export`; `app/reports/export` → `/app/reports/export`;
`app/transactions/export` → same path (alias of `/app/wallet/transactions/export`); `app/sender-ids/{id}/documents/{i}` →

(update the provider-side URLs to the API host); `internal/worker/tick` → `/internal/worker/tick`
(prefer `schedule:run`); `/api/health` → `/api/v1/health`.

## 8. Deployment (https://smsbackend.hivelabsbd.com)

1. Document root = `backend/public` (subdomain setting in hPanel). If the host cannot point at
   `public/`, the root `backend/.htaccess` rewrites everything into `public/` and denies otherwise, so
   `.env`, `storage/`, `vendor/`, `database/`, `composer.json`, `artisan` are never served.
2. Upload without `.env`/`vendor` from your machine; on the server: `composer install --no-dev
   --optimize-autoloader`, create `.env` from `.env.example`, `php artisan key:generate`.
3. Database: `php artisan migrate --force` — the baseline migration only **records** the existing 42
   tables; it adds Laravel's `jobs`, `failed_jobs`, `job_batches`, `cache`, `cache_locks`,
   `migrations`. Inspect first with `php artisan migrate --pretend`. **Never** `migrate:fresh`,
   `migrate:reset`, `migrate:rollback` or `db:wipe` on production.
4. `php artisan storage:link` is **not** needed (documents are private). Make `storage/` and
   `bootstrap/cache/` writable.
5. `php artisan config:cache route:cache view:cache` (or `php artisan optimize`); after every
   deploy: `php artisan optimize:clear && php artisan optimize && php artisan queue:restart`.
6. Cron (hPanel → Cron Jobs), one entry:
   `* * * * * cd /home/<user>/domains/smsbackend.hivelabsbd.com/backend && /usr/bin/php artisan schedule:run >> /dev/null 2>&1`
7. Switch background work **once**: disable the Next.js worker cron (`/api/internal/worker/tick`)
   when this scheduler starts (both are safe together, but one is enough).
8. Point provider callbacks to `https://smsbackend.hivelabsbd.com/api/v1/webhooks/sms/<provider>`
   and `/api/v1/webhooks/payments/<provider>`.
9. Verify: `GET /api/v1/health`; `GET /api/v1/internal/ready` with `Bearer <CRON_SECRET>` (503 if a
   dependency or the SMS provider is not production-ready); `php artisan schedule:list`.
10. Logs: `storage/logs/laravel-YYYY-MM-DD.log` (`LOG_STACK=daily`, `LOG_LEVEL=warning`); every
    line of a request carries `requestId`. Passwords, tokens, keys and message bodies are never logged.

On a VPS: run `php artisan queue:work --tries=3 --max-time=3600` under Supervisor/systemd and set
`QUEUE_WORKER_VIA_SCHEDULER=false`; Redis can replace the database cache/queue.

## 10. Known issues / limits

- `HttpSmsProvider` and `SslCommerzProvider` are unverified scaffolding (same as Node): configure
  and test against the real provider sandbox before going live (`/internal/ready` fails while the
  production provider is `mock`).
- Hostinger shared hosting has no long-running workers: queued jobs run within ≤ 1 minute via the
  scheduler; API messages still go out immediately after the response (`DispatchMessagesJob`).
- Contact import status lives in the cache (24 h) because the schema has no import table.
- Laravel 12 security support ends February 2027 — upgrade to Laravel 13 (PHP ≥ 8.3) before then.
- Dashboard/admin JSON is camelCase while the customer API stays snake_case (contract); the six
  pre-existing admin endpoints keep their snake_case shapes.

## 11. Decisions that differ from the original request (all explained in doc 10)

`/api/v1/app/*` prefix for dashboard routes (the unprefixed `/messages` and `/sender-ids` are the
customer API); validation `details.fields[]` shape kept; no Sanctum; BD-only numbers; no dashboard
"quick send" endpoint (all dashboard sends are campaigns, subject to the account's review policy);
`messages` table remains the SMS queue (jobs drive it).
